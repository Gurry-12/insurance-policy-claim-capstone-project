# ER Diagram

> Authoritative entity-relationship diagram for `insurance_db`: all 17 physical tables, primary/foreign keys, relationship cardinalities, per-entity notes, and the naming strategy that maps the 16 JPA entities onto those tables.

## Purpose

This document is the single source of truth for the **diagram-level** view of the `insurance_db` schema. It answers "which tables exist, how they are connected, and at what cardinality." Column-level detail belongs in [`Table_Descriptions.md`](Table_Descriptions.md), constraint detail in [`Constraints.md`](Constraints.md), and the relationship narrative in [`Entity_Relationships.md`](Entity_Relationships.md).

Who reads it: developers onboarding to the data model, database/backend engineers validating schema changes, and reviewers cross-checking the schema against the entity layer.

## Overview

The database is MySQL 8, schema `insurance_db`, and is managed entirely by Hibernate through `spring.jpa.hibernate.ddl-auto=update` (see `insurance-policy-claim-management-system/src/main/resources/application.properties`). There are **16 JPA entities** in `com.insurance.demo.model`, which map to **17 physical tables** because `PolicyPlan.allowedDurations` is an `@ElementCollection` that materializes as the extra join table `policy_plan_durations`.

The model clusters into four functional groups:

- **Identity & access**: `users`, `refresh_tokens`, `customers`, `staff_specialities`, `otp_verifications`.
- **Catalog & pricing**: `insurance_products`, `policy_plans`, `policy_plan_durations`, `coverage_options`, `pricing_rules`, `pricing_audit_logs`.
- **Sales**: `quotes`, `policies`, `premium_payments`.
- **Claims**: `claims`, `claim_documents`, `claim_status_histories`.

## Business Context

The diagram reflects the business domain documented in [`../02_Business_Domain/Insurance_Domain.md`](../02_Business_Domain/Insurance_Domain.md): one identity (`users`) that can be a customer, an internal-staff member, or an admin; products that contain plans, each with coverage tiers and pricing rules; quotes that capture a priced proposition; policies that snapshot the pricing at purchase; payments that activate policies; and claims with documents and an append-only status history. Nothing here duplicates that narrative — this document shows the physical shape, that document explains the business rules.

## Technical Design

### Physical naming strategy

All entity field names are camelCase and all physical column names are snake_case. Spring Boot configures Hibernate with the default physical naming strategy (referred to in this repo as `SpringPhysicalNamingStrategy`), which converts each `camelCase` field into a `snake_case` column automatically. For example:

- `fullName` → `full_name`
- `mobileNumber` → `mobile_number`
- `isActive` → `is_active`
- `policyNumber` → `policy_number`
- `expiresAt` → `expires_at`

Explicit `@Column(name = "...")` overrides take precedence (e.g. `premium_payments.payment_id`, `claim_documents.document_name`). No custom naming bean is configured in `application.properties`, so the Spring Boot default applies.

### Per-entity notes

1. **`users`** — Identity and auth principal; email, mobile_number and role drive login and authorization; token_version supports refresh-token family revocation.
2. **`refresh_tokens`** — Opaque, hashed refresh sessions; one per active session, many per user over time; explicit indexes on jti (unique), user_id, token_hash and expires_at.
3. **`customers`** — One-to-one customer profile owned by the users row; only `user_id` is required at creation, the rest is filled before purchase.
4. **`staff_specialities`** — One-to-one staff-to-product-type mapping; the `user_id` column is unique so each staff member has exactly one speciality.
5. **`otp_verifications`** — Dual email+SMS OTP records; one user accumulates many rows, queries always take the latest by created_at.
6. **`insurance_products`** — Catalog product header; product_name is unique; is_active gates customer-facing availability.
7. **`policy_plans`** — A versioned plan inside a product; snapshot of premium type and terms; owns the durations element collection.
8. **`policy_plan_durations`** — Join table synthesized by `@ElementCollection`; holds only `(plan_id, duration)`; no entity class and no surrogate key.
9. **`coverage_options`** — Selectable coverage tiers per plan; ordered by display_order.
10. **`pricing_rules`** — Versioned pricing per plan (base risk rate, processing fee, GST); status ACTIVE/INACTIVE with effective windows.
11. **`pricing_audit_logs`** — Append-only audit of pricing rule changes; references pricing_rule_id as a plain column (no FK constraint).
12. **`quotes`** — Priced proposition snapshot for a customer+plan; expires_at enforces the quote TTL; status tracks CREATED→USED/EXPIRED/CANCELLED.
13. **`policies`** — The active contract; snapshots pricing and plan version at purchase; @Version optimistic lock; quote_id records the originating quote.
14. **`premium_payments`** — Payment ledger; PK column is named `payment_id` (not `id`); transaction_reference is unique to prevent double processing.
15. **`claims`** — Claim records against a policy; claim_number unique; assigned_staff_id optional until a staff member takes it; @Version optimistic lock.
16. **`claim_documents`** — Cloudinary-backed document metadata per claim; the binary lives in Cloudinary, this table holds the reference.
17. **`claim_status_histories`** — Append-only timeline of claim status changes; previous_status/new_status are plain strings, not FK references.

## Workflow

The schema is produced automatically on application startup:

1. The app boots with `spring.jpa.hibernate.ddl-auto=update` (backend port 8081, schema `insurance_db`).
2. Hibernate validates the entity mappings and emits `ALTER TABLE`/`CREATE TABLE` statements for any missing tables, columns, or constraints; it never drops existing objects.
3. The `refresh_tokens` `@Index` definitions and all unique constraints are applied at this point.
4. To verify this diagram against the live database, diff each entity in `model/*.java` against `SHOW CREATE TABLE <name>` in MySQL and update this document when they diverge.

## Best Practices

- The entity annotations are the single source of truth; keep this diagram in sync by regenerating it from `model/*.java` rather than editing the diagram in isolation.
- Prefer explicit `@Column(name = "...")` on every field so the physical name does not silently depend on the naming strategy.
- Document the four eager `@ManyToOne` associations (see [`Entity_Relationships.md`](Entity_Relationships.md)) — they are pure overhead on reads and are targeted for LAZY conversion in [`../06_Backend/Performance.md`](../06_Backend/Performance.md).
