# DTOs Overview

## Purpose

This document explains all Data Transfer Objects (DTOs) in the system — why they exist, what they carry, validation rules, and how they are mapped to/from entities.

---

## Why DTOs?

DTOs (Data Transfer Objects) serve several critical purposes:

1. **Security:** Prevent exposing sensitive entity fields (e.g., hashed passwords, internal IDs)
2. **API Contract:** Define exactly what the client sends and receives, independent of entity structure
3. **Validation:** Bean validation annotations belong on DTOs, not entities
4. **Versioning:** API shape can change without changing database entities
5. **Performance:** Only send the data needed, not full entity graphs

---

## DTO Packages

```
dto/
├── request/    ← 18 request DTOs (what client sends)
└── response/   ← 16 response DTOs (what server returns)
```

## Request DTOs

### `LoginRequestDTO`
**Used in:** `POST /api/auth/login`

```java
email        @NotBlank @Email
password     @NotBlank
```

**Note:** Password is hashed via BCrypt before storage.

---

### `UserRequestDTO`
**Used in:** `POST /api/auth/register`

```java
fullName     @NotBlank @Pattern(letters+spaces) @Size(2-100)
email        @NotBlank @Email
password     @NotBlank
mobileNumber @NotBlank @Pattern(international format: +91XXXXXXXXXX)
```

**Why mobile pattern?** The system uses Twilio for SMS. International format (+country-code + number) is required by Twilio's API.

---

### `VerifyOtpRequest`
**Used in:** `POST /api/auth/verify-otp`

```java
email        @NotBlank @Email
emailOtp     @NotBlank
phoneOtp     @NotBlank
```

---

### `ResendOtpRequestDTO`
**Used in:** `POST /api/auth/resend-otp`

```java
email        @NotBlank @Email
phone        @NotBlank ← used to verify identity before resending
```

**Why require phone too?** To prevent someone from resending OTPs to an email they don't own.

---

### `ForgotPasswordRequestDTO`
**Used in:** `POST /api/auth/forgot-password`

```java
email        @NotBlank @Email
```

---

### `ResetPasswordRequestDTO`
**Used in:** `POST /api/auth/reset-password`

```java
email        @NotBlank @Email
emailOtp     @NotBlank
phoneOtp     @NotBlank
newPassword  @NotBlank @Size(min=8)
```

---

### `CustomerRequestDTO`
**Used in:** `POST /api/customers/profile`, `PUT /api/customers/{id}`

```java
dateOfBirth     @Past (must be in the past)
address         @NotBlank
city            @NotBlank
state           @NotBlank
pinCode         @Pattern(6 digits)
nomineeName     @NotBlank
nomineeRelation @NotBlank
```

**Why `@Past` on dateOfBirth?** Prevents future dates. Service layer additionally validates age ≥18.

---

### `InsuranceRequestDTO`
**Used in:** `POST /api/products`

```java
productName    @NotBlank @Size(2-100)
productType    @NotNull  ← ProductType enum
description    @NotBlank @Size(min=10)
isActive       @NotNull
```

---

### `ProductRequestDTO`
**Used in:** `PUT /api/products/{id}`

```java
productId      @NotNull
productName    @NotBlank
productType    @NotNull
description    @NotBlank
isActive       @NotNull
```

**Why separate from InsuranceRequestDTO?** Update requires ID; create does not.

---

### `PlanRequestDTO`
**Used in:** `POST /api/plans`, `PUT /api/plans/{id}`

```java
productId          @NotNull
planName           @NotBlank @Size(2-100)
coverageAmount     @NotNull @Positive
premiumAmount      @NotNull @Positive
premiumType        @NotNull ← ONE_TIME or ANNUAL
duration           @NotNull @Positive @Max(40)
termsAndConditions @NotBlank
isActive           @NotNull
```

**Why `@Max(40)` on duration?** Insurance policies rarely exceed 40 years. Protects against data entry errors.

---

### `PolicyPurchaseRequestDTO`
**Used in:** `POST /api/policies/purchase`

```java
planId     @NotNull
startDate  @NotNull ← customer chooses start date
```

**Note:** `endDate` is NOT in this DTO — it's calculated by the service as `startDate + plan.duration years`.

---

### `PolicyIssueRequestDTO`
**Used in:** `POST /api/policies/issue`

```java
customerId @NotNull ← admin/staff provides target customer
planId     @NotNull
startDate  @NotNull
```

**Difference from purchase:** The issuer provides `customerId` explicitly because they're acting on behalf of a customer.

---

### `PaymentRequestDTO`
**Used in:** `POST /api/payments`

```java
policyId       @NotNull
amount         @NotNull @Positive
paymentMode    @NotNull ← PaymentMode enum
paymentStatus  ← PaymentStatus enum (SUCCESS or FAILED)
```

**Note:** `transactionReference` is NOT in the DTO — it's auto-generated by the server via `TransactionReferenceGenerator`.

---

### `ClaimRequestDTO`
**Used in:** `POST /api/claims/raise` (multipart, part "claim")

```java
policyId      @NotNull
claimAmount   @NotNull @Positive
claimReason   @NotBlank
incidentDate  @NotNull ← LocalDate
```

**Note:** Files come as separate multipart part ("files"), not inside this DTO.

---

### `ClaimReviewRequestDTO`
**Used in:** `PATCH /api/claims/{id}/review` (staff), `PATCH /api/claims/{id}/final-decision` (admin)

```java
recommendedStatus  @NotNull ← ClaimStatus enum
remarks            @NotBlank
```

**Staff allowed values:** RECOMMENDED_FOR_APPROVAL, RECOMMENDED_FOR_REJECTION  
**Admin allowed values:** APPROVED, REJECTED  
Validation of which values are allowed happens in service, not DTO.

---

### `ClaimDocumentRequestDTO`
**Used in:** document upload (not directly; files are MultipartFile)

```java
documentName  @NotBlank
documentType  @NotBlank
```

---

### `CreateStaffRequestDTO`
**Used in:** `POST /api/users/staff`

```java
fullName          @NotBlank @Pattern @Size(2-100)
email             @NotBlank @Email
password          @NotBlank
mobileNumber      @NotBlank @Pattern
productSpeciality @NotNull ← ProductType enum
```

**Why no `role` field?** Staff accounts are always `ROLE_INTERNAL_STAFF`. The service sets this hardcoded. Admin cannot choose the role.

---

### `UserStatusUpdateRequestDTO`
**Used in:** `PATCH /api/users/{id}/status`

```java
isActive  @NotNull
```

## Response DTOs

### `ApiResponseDTO<T>`
**Used in:** ALL endpoints as the outer wrapper

```java
String message      ← success/info message
boolean success     ← always true for 2xx responses
T data              ← the actual response payload
LocalDateTime timestamp
```

---

### `ErrorResponseDTO`
**Used in:** Error responses (4xx, 5xx)

```java
LocalDateTime timestamp
int statusCode
String errorType    ← HTTP status name (e.g., "NOT_FOUND")
String message      ← human-readable error
String requestPath  ← which URL failed
```

---

### `ValidationErrorResponseDTO`
**Used in:** `MethodArgumentNotValidException` (422-style validation failures)

```java
LocalDateTime timestamp
int statusCode
String errorType      ← "VALIDATION_FAILED"
String message        ← "Validation Failed."
String requestPath
Map<String, String> fieldErrors  ← { "fieldName": "error message" }
```

---

## DTO-to-Entity Mapping

### ModelMapper Usage

`ModelMapper` (v3.2.0) is configured as a Bean in `AppConfig.java`. It handles most field-to-field mapping automatically when field names match.

**Used for:**
- `UserRequestDTO` → `AppUser` (in `AuthServiceImpl.registerUser`)
- `AppUser` → `UserResponseDTO`
- `PremiumPayment` → `PaymentResponseDTO`
- Various response mappings

**Manual mapping (when ModelMapper isn't sufficient):**
`ClaimResponseDTO`, `PolicyResponseDTO` are built manually in service methods because they combine data from multiple entities.

---

## Common DTO Mistakes

1. **Do NOT expose passwords (even hashed) in response DTOs**
2. **Do NOT skip `@Valid` on controller parameters** — DTO validations won't run
3. **Do NOT put business logic in DTOs** — they are pure data containers
4. **Do NOT reuse request DTOs as response DTOs** — they have different concerns
5. **Always use `BigDecimal` for monetary amounts** — never `double` or `float`
